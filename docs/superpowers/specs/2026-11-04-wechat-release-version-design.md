# release 小程序上传版本自动递增方案

状态：用户已确认，实现与本地验收已完成；未真实上传、未推送实现代码

## 目的与已确认规则

用户选择由仓库维护版本记录，避免每次上传手动指定版本号。仅处理 `juya-miniapp` 的 `release` 生产包；测试包沿用原流程。

- 根据最近一次**成功上传**的生产包递增最后一段，不等待微信审核或正式上线：`1.0.0 → 1.0.1 → 1.0.2`，`1.0.9 → 1.0.10`
- 单纯本地构建不消耗版本；明确上传失败不更新成功记录
- 初始记录采用已有的 2026-11-04 官方 CLI 成功上传回执：`1.0.0` / `100`，源码 `982976f1827a2383a0c7a5a8e9816f931d9b4c48`。这表示最后一次已知成功上传，不声称已正式上线
- 微信上传版本与构建清单 `versionName` 一致；`versionCode` 从 `100` 按成功上传次数递增

## 方案比较

1. 每次读取微信后台版本：可以反映人工上传，但依赖后台登录；官方查询 API 对普通账号不可直接使用
2. 仓库保存成功上传版本：不依赖后台查询，能随 Git 接续；绕过流程人工上传后需要核对并更新记录

用户选择方案二。实现采用项目已有 Node.js 脚本、pnpm 与微信官方开发者工具 CLI，不引入第三方平台或新服务。

## 固定入口与处理顺序

新增 `pnpm release:mp-weixin`，固定执行构建和上传，不再要求传入版本号。

1. 检查当前确为 `release`，工作区无未提交源码，并与远程 `release` 同步；失败则停止，不自动切分支、合并或丢弃改动
2. 从 `release/wechat-version.json` 读取最后成功版本，校验格式并计算候选版本；使用同仓库共享锁避免本机多个工作树同时发布
3. 使用独立构建目录和生产配置生成候选包，校验页面与主包预算，验证构建清单版本与上传版本一致；保留日常开发、测试输出
4. 调用已登录微信开发者工具的官方上传命令；支持私有环境变量指定 CLI 路径以适配不同电脑，不保存账号或密钥
5. 成功后更新版本记录与相应清单，记录实际源码提交及上传结果
6. 自动创建仅包含发布记录及清单的中文规范 Git 提交，并推送 `release`，以便下一次或换电脑从最新记录继续

新增 `--dry-run` 只显示当前记录与下次版本，不构建、上传、提交、推送或修改文件；新增 `--build-only` 用候选版本构建并校验，不上传、不推进记录。

原 `build:mp-weixin` 等普通构建命令保持现状，不自动上传。更新 `AGENTS.md`、`HANDOFF.md` 和操作说明，要求后续 release 上传统一使用新入口，不再使用一次性脚本手填版本。

## 失败及接续

- 构建失败、微信明确拒绝上传：成功记录保持原值，修复后重试同一候选版本
- 上传中断或回执不明确：保留待核对状态，阻止盲目重用或递增；先在微信后台确认上传结果，再完成或取消待处理记录
- 微信成功但 Git 提交或推送失败：保留成功回执和新版本，阻止再次上传；提供只补保存/同步记录的恢复入口，绝不重新上传同一包
- 多台电脑按顺序使用并先同步 Git；本轮不建设跨机器的发布锁服务，不支持同时从两台电脑上传
- 手动绕过新命令上传或人为修改版本后，先核对微信后台并更新仓库记录

## 范围与验收

只修改小程序仓库。实现与验收使用模拟上传器，不实际上传、不切换体验版、不提审、不正式发布，也不操作 API、后台或数据库。本轮不自动推送实现代码；上述自动提交和推送是未来用户执行发布命令时的明确行为，需随方案确认。

验收覆盖连续成功上传、未上线再次上传、构建与上传失败、跨位递增、非 release 拒绝、记录损坏、过期 Git 状态、并发锁、上传结果不明确及 Git 同步失败后的恢复。执行完整测试、静态检查与生产候选包构建，确认没有真实上传或消耗版本号。
